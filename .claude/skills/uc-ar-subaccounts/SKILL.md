# ลูกหนี้ UC แยกบัญชีย่อย (PPFS, Instrument, HC, AE, CR)

ระดับความเชื่อมั่นของแต่ละข้อระบุไว้ท้ายข้อ: **[ผัง 2569]** = ผังบัญชีภาคสุขภาพ ปีงบ 2569 สป.สธ. (ตรวจจากเอกสารจริง), **[สปสช. 2569]** = แนวทางปฏิบัติการขอรับค่าใช้จ่าย ปีงบ 2569 ของ สปสช., **[แนวทาง 2565]** = แนวทางบันทึกบัญชี UC (เอกสารอบรม 19 เม.ย. 2565 รุ่นเก่า หลักการยังใช้ได้แต่ต้องเทียบรหัส), **[ระบบเรา]** = ตรวจจากฐาน insight/his ของ repo นี้ด้วย db-cli, **[อนุมาน]** = ข้อสรุปที่ยังไม่มีเอกสารยืนยันตรง ต้องถามบัญชีของ รพ. ก่อนใช้

## 3. ยอดที่ REP ของ รพ. เราแยกมาจริง [ระบบเรา]

`rep_row.fund_amounts` (insight, jsonb) เก็บยอดแยกตามกองทุนย่อยจากไฟล์ REP ที่ `/fund/rep-import` นำเข้า key ที่พบจริง (นับทั้งฐาน ณ 14 พ.ย. 2569):

- IP: `ผู้ป่วยใน (IP) / IPINRGR` (ปกติ), `IPAER`, `IPAEC`, `IPINRGC` ; `โรคเฉพาะ (DMIS) / CATARACT`, `CATINST`, `CATARACT / ค่าภาระงาน(รพ.)` ; `อุบัติเหตุฉุกเฉิน (AE) / CAREF`, `IPNB`, `IPUC`, `CAREF-PUC` ; `อวัยวะเทียม/อุปกรณ์บำบัดรักษา (INST) / INST` ; `DRUG`
- OP: `อวัยวะเทียม/อุปกรณ์บำบัดรักษา (INST) / OPINST` ; `โรคเฉพาะ (DMIS) / PP`, `Paliative Care`, `DM` ; `อุบัติเหตุฉุกเฉิน (AE) / OPAE (1.1*4*5)`, `CARAE` ; `ค่าใช้จ่ายสูง (HC) / OPHC` ; `ผู้ป่วยใน (IP) / IP-ONTOP` ; `DRUG` ; `FS`
- `rep_row` ยังมี `central_reimburse` (ยอด CR รวมต่อแถว), `net_nhso`, `claim_total`, `main_fund`, `sub_fund` ใช้แยก/ตรวจยอด CR ได้

key ใน REP จึงจับคู่บัญชีได้ตรงๆ: `INST/OPINST/CATINST` → CR, `AE /*` → CR (OP) หรือ IP ตาม patient_type, `HC / OPHC` → CR, `DMIS / PP` → .209, `CATARACT` → CR

## 4. สมุดลูกหนี้ของระบบเรายังไม่แยกบัญชีย่อยเหล่านี้ [ระบบเรา]

- `src/app/api/fund/ar-sync/ledger.ts` ตั้งลูกหนี้ UCS ตาม hospmain/จังหวัดเท่านั้น (`UC_OP_ACCOUNTS`: .201 ใน CUP, .203 ในจังหวัด, .204 ต่างจังหวัด, 1102050102.201 นอกสังกัด) และ IP → .202 ทั้งก้อน
- ยอด ณ 14 พ.ย. 2569: .201 OP 34,219 แถว 33,549,012.13 บาท ; .202 IP 3,438 แถว 31,447,541.47 ; .203 / .204 / 1102050102.201 รวมราว 0.57 ล้าน ; ไม่มีบัญชี 84 แถว 44,334.50 ; **ไม่มีแถวใดลง .209 / .216 / .217 / .222**
- ผังบัญชีใน `ar_account` มีครบทุกบัญชีในข้อ 1 แล้ว แก้ mapping ได้ที่ `/admin/ar-accounts` แต่ mapping ปัจจุบันเป็นระดับ สิทธิ × OP/IP ไม่ใช่ระดับรายการ

## 5. ทางเลือกในการแยก (ต้องให้ผู้ใช้/งานบัญชีเลือกก่อนลงมือ)

1. **ตั้งตอนให้บริการ (ตามหลักบัญชีที่ถูก)**: แยกยอดของ visit/admission เป็นส่วน CR / P&P / ปกติ จากรายการค่าใช้จ่ายใน HOSxP (เช่น อุปกรณ์ที่มีรหัส ADP ของประกาศอุปกรณ์ฯ, รายการ PP fee schedule, เคส AE ข้ามจังหวัด) ต้องมีตารางจับคู่ รหัสรายการ → กองทุน ซึ่ง HOSxP แต่ละ รพ. ตั้งไม่เหมือนกัน เสี่ยงแยกผิด
2. **โอนจัดประเภท (reclass) ตอน REP/Statement กลับ**: ใช้ยอดใน `rep_row.fund_amounts` ลงรายการปรับปรุง Dr .216/.217/.209 / Cr .201/.202 ตามยอดจริงที่ สปสช. แยกมา ง่ายและตรงกับเงินจริง แต่ลูกหนี้ CR จะปรากฏช้า (หลัง REP) และต้องไม่ลงซ้ำเมื่อ REP ฉบับใหม่ของรายเดิมเข้ามา
3. **รายงานอย่างเดียว**: ยังไม่ลงบัญชี แค่แสดงยอดลูกหนี้ .201/.202 แยกส่วน CR/P&P ตาม REP ให้งานบัญชีเอาไปลงเอง

กติกาที่ต้องรักษาเสมอ: แถวใน `ar_ledger` ที่ลงแล้วห้ามแก้ ส่วนต่างหรือการโอนจัดประเภทลงเป็นแถวใหม่ (ดู AGENTS.md หัวข้อสมุดลูกหนี้)

## 6. สิ่งที่ยังต้องยืนยันกับงานบัญชีของ รพ.

- AE / HC / HC_DRUG / AE_DRUG ลง .216/.217 ทั้งหมดหรือไม่ (ผัง 2569 ไม่มีบัญชีแยก แต่ไม่พบหนังสือที่เขียนตรงๆ)
- OPAE ในจังหวัด (ไม่ข้ามจังหวัด) ลงบัญชีใด
- P&P ของสิทธิอื่นที่ไม่ใช่ UC ลง .209 ด้วยตามคำอธิบายผัง ("ทุกสิทธิ") หรือแยกตามสิทธิเดิม
- รหัส ADP/รายการใน HOSxP ของ รพ. ที่ใช้ระบุอุปกรณ์ CR และ PP fee schedule

## 7. โปรแกรมที่ รพ. ใช้จริงตั้งลูกหนี้จาก HOSxP อย่างไร (อ่านโค้ดจริง 14 พ.ย. 2569)

ทุกตัวที่พบ**ไม่เขียนลง HOSxP เลย** อ่านอย่างเดียวแล้วเก็บลูกหนี้ในฐานของตัวเอง เหมือนระบบเรา (`hisQuery` read-only + ฐาน insight)

**smart-statement** (`github.com/itplaiprayahos-ppy/smart-statement`, Node + PostgreSQL ฐาน `claim_recon` แยกจาก HOSxP v4)
- ต่อ HOSxP ด้วย role อ่านอย่างเดียว (แนะนำเครื่อง replica) และตั้ง `default_transaction_read_only=on` ทุก connection
- **ยอดเรียกเก็บคิดจาก `opitemrece` ตอนดึง ไม่ใช้ `vn_stat.uc_money`** เพราะ `vn_stat` คำนวณไว้ ณ จุดเวลาหนึ่ง รายการที่เพิ่ม/แก้ทีหลังไม่ตาม (พบ visit ที่ `uc_money` = 0 แต่มีรายการลูกหนี้สิทธิ) ยอดเรียกเก็บ = รวม `sum_price` ที่ `paidst = '02'` (ลูกหนี้สิทธิ) ; paidst: 00 ค้างชำระ, 01 ชำระเองเบิกได้, 02 ลูกหนี้สิทธิ, 03 ชำระเองเบิกไม่ได้, 04 ส่วนลดเงินสด
- **แยก visit เข้ากองทุนย่อย (HC, ยามะเร็ง, AE, INST, DMIS, PP)** ด้วยตารางตั้งค่าในฐานตัวเอง: กองทุน ← รายการ icode จาก `nondrugitems`/`drugitems` (มีอย่างน้อย 1 รายการ) + กรองรหัสสิทธิ (`pttype`) + ICD-10 (รหัสเดี่ยว/ช่วง) ; PP แยก "กิจกรรมย่อย" (รายการ + ICD ของกิจกรรมเดียวกัน) ; ยอด "ตั้งเบิก (กองทุน)" = ราคารวมของรายการที่เข้าเกณฑ์ (ซ้ำนับครั้งเดียว) ; ยอด "ได้รับ (กองทุน)" = คอลัมน์ของกองทุนนั้นใน REP (`HC / OPHC` ฯลฯ) ; มีหน้า "ตรวจย้อนกลับ" = REP จ่ายกองทุนแต่ visit ไม่เข้าเกณฑ์ตามการตั้งค่า ใช้หาว่าตั้งรายการขาดอะไร
- จับคู่ REP กับ visit: เลขบัตร + วันที่รับบริการ (ไม่มีเลขบัตรใช้ HN + วันที่) ; มาหลายครั้งในวันเดียวจับคู่ 1:1 ตามลำดับยอดและติดป้ายให้คนตรวจ ; REP ซ้ำรอบใช้ TRAN_ID รวมยอด (รวมยอดปรับลดติดลบ) ; Statement (โอนจริง) เชื่อม REP ด้วย TRAN_ID เก็บแยกตารางจาก REP กันนับซ้ำ

**accloei / AR Management** (`github.com/iamharin/accloei`, MySQL ฐาน `ar_management` แยกจาก HOSxP)
- ตาราง `chart_of_accounts` หนึ่งแถว = บัญชีลูกหนี้ + กติกาดึง: `source_type = 'pttype'` (ตามสิทธิ + OPD/IPD) หรือ `'query'` (SQL กำหนดเองบน HOSxP) พร้อม `priority` (น้อยทำก่อน) **บัญชีพิเศษ (เช่น HC, CR) ใช้ custom query ลำดับก่อน แล้วบัญชีตามสิทธิรับส่วนที่เหลือ**
- `accounts_receivable` เก็บ `ar_amount`, `original_ar_amount`, `paid_amount`, `balance`, `status` (pending/approved/adjusted/paid/cancelled), `submission_status` (draft/submitted/recorded), `rep_approved_amount`, `statement_approved_amount`, `payment_source` ; มีคำขอปรับปรุงแบบอนุมัติ และ `journal_entries` Dr/Cr
- ผังในฐานตัวอย่างมี .218/.219 "UC OP/IP - HC" และ .220/.221 "UC OP/IP - DMI" ซึ่ง**ไม่มีในผัง 2569** (และไม่มีใน `ar_account` ของเรา) อย่าเพิ่มตามโดยไม่ถามงานบัญชี
- ข้อควรระวัง: การจับคู่ Statement ใช้ `hn = ? OR vn = ? OR an = ? OR cid = ?` แล้วเอาแถวล่าสุดแถวเดียว ผิดได้ง่ายเมื่อคนไข้มีหลาย visit อย่าเลียนแบบ

**บทเรียนสำหรับระบบเรา**
- โครงสร้างเราถูกทางแล้ว (อ่าน HOSxP อย่างเดียว ลงลูกหนี้ใน insight แถวที่ลงแล้วไม่แก้ ส่วนต่างเป็นแถวใหม่ ซึ่งตรวจย้อนได้ดีกว่าแบบ update ยอดในแถวเดิมของ accloei)
- **พิสูจน์แหล่งยอดแล้ว (db-cli 14 พ.ย. 2569) ไม่ต้องเปลี่ยน:** OPD visit 1–7 พ.ย. 2569 ที่มีรายการ `paidst = '02'` 3,850 VN ตรงกับผลรวม `rcpt_debt` (ทุก debt ของ VN ไม่นับ ABORT/ที่ยกเลิก) 3,815 VN (99.1%) ส่วนที่เหลือ: ไม่มี debt 7 VN 5,628.50 บาท (ยังไม่ปิด visit), แก้รายการหลังตั้ง debt 3 VN, ต่างเล็กน้อย 25 VN ; IPD จำหน่าย ต.ค. 2569 ที่ `finance_lock = 'Y'` `an_stat.uc_money` ตรง 662/664 AN ต่างรวม 1.10 บาท ข้อควรระวัง: 1 VN มีหลาย debt คนละวันได้ เทียบรายวันตาม debt_date จะเห็นต่างผิดๆ ต้องเทียบตาม VN
- **ตารางตั้งค่ากองทุนย่อยทำแล้ว:** `ar_fund_rule` (insight) + หน้า `/admin/ar-funds` (เงื่อนไข = หมวดรายรับ หรือ icode ของรายการ paidst 02 + กรอง ICD-10 ขึ้นต้น + กองทุนหลัก, เทียบคอลัมน์ REP รายเดือน: ตรงกัน / เข้าเกณฑ์แต่ REP ไม่จ่าย / REP จ่ายแต่ไม่เข้าเกณฑ์) ยังไม่แยกบัญชีใน ar-sync ; ส.ค. 2569: INST (หมวด 02) HOSxP 89 VN vs REP 76 VN ตรงกันครบทั้ง 76 ; PP (หมวด 21) 503 VN vs REP 150 VN = หมวด 21 กว้างเกิน ต้องระบุ icode ; HC/AE ยังไม่มีเงื่อนไข (AE OP จ่ายตามเงื่อนไข visit ไม่ใช่รายการ)
- จับคู่กับ REP ด้วย VN/AN (`rep_row.seq_no`/`an`) ตามที่ทำอยู่ ดีกว่าเลขบัตร + วันที่ ส่วน REP ซ้ำรอบใช้ `tran_id` ล่าสุด
